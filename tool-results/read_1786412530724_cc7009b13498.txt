     1→# VORTEX — OSR (On-Stack Replacement) Bug Report
     2→
     3→**Repository audited:** https://github.com/AVmakeralt/VORTEX
     4→**Scope:** All OSR-related code paths — `vtx_osr_up`, `vtx_osr_down`, the inline-asm trampoline, side-table OSR entry registration, the real deopt path (`vtx_deopt_runtime_transition`), stack walking, GC interaction, and the dispatch-loop OSR trigger.
     5→**Method:** Direct source read of `osr.c` / `osr.h` / `frame_state.h` / `side_table.h` / `stack_walk.c` / `deopt_stubs.c` / `dispatch.c` / `codegen.c` / `frame_layout.h`, plus 4 parallel sub-agents for cross-cutting concerns. Every Critical and High bug below was verified by direct source read.
     6→
     7→---
     8→
     9→## 1. Executive Summary
    10→
    11→The OSR subsystem is the most broken part of the VORTEX JIT. It is not just buggy — large parts of it are **dead code**, and the parts that are live have fundamental correctness flaws that would cause silent wrong-code execution or crashes on the very first OSR transition.
    12→
    13→The single most important finding is that **the entire `vtx_osr_down` path is dead code**. The actual runtime deopt path (`vtx_deopt_runtime_transition` in `baseline/deopt_stubs.c`) retrieves the FrameState and register map from the side table into local variables, then **never uses them** — it reads locals and stack directly from JIT frame slots instead. This means every bug in `osr.c`'s OSR-down path (and there are many) is latent, and every assumption the design makes about FrameState-driven reconstruction is unverified in practice.
    14→
    15→The second most important finding is that **`VTX_STF_OSR_ENTRY` is never written by any code generator**. The flag is defined in `side_table.h:79`, read by `vtx_osr_up` at `osr.c:253`, but no codegen path (T1 baseline, T2 SoN, T3 speculative, AOT) ever passes it to `vtx_side_table_add_entry`. This means the side-table lookup in `vtx_osr_up` (lines 247–260) will never find an OSR entry — `vtx_osr_up` only succeeds via the `bc_pc_map` fallback (lines 265–274), and only for T1-compiled methods that happen to have a `bc_pc_map` entry at the loop header PC.
    16→
    17→The third key finding is the **OSR-up return-value bug** (`OSR-ASM-2`): after the JIT code finishes and returns via its epilogue, RAX contains the JIT method's return value (a NaN-boxed `vtx_value_t`), but the C caller (`vtx_interp_run`) reads AL as the `bool` return of `vtx_osr_up`. When the method returns SMI 0 or `undefined` (low byte 0), `osr_ok` is false and the dispatch loop sets `jit_reenter_pending`, causing the entire method to be re-executed from PC 0 on the next call — side effects run twice.
    18→
    19→**Total OSR-specific bugs found: 33** (across 4 audit dimensions, after removing 2 false positives).

    22→|----------|-------|
    23→| Critical | 10 |
    24→| High | 12 |
    25→| Medium | 7 |
    26→| Low | 4 |
    27→| **Total** | **33** |

    31→## 2. The Three "Killer" Bugs
    32→
    33→These three bugs together mean that OSR in VORTEX is fundamentally non-functional for any non-trivial program. They should be fixed before anything else.
    34→
    35→### Killer #1: `vtx_osr_down` is dead code
    36→
    37→**Files:** `src/deopt/osr.c:520-612` (defines `vtx_osr_down`), `src/baseline/deopt_stubs.c:541-818` (defines `vtx_deopt_runtime_transition` — the real path).
    38→
    39→**Verification:** I grepped for every call site of `vtx_osr_down`:
    40→```
    41→$ grep -rn "vtx_osr_down\b" src/ cpp/
    42→src/deopt/osr.h:190  ← declaration
    43→src/deopt/osr.c:520  ← definition
    44→```
    45→Zero call sites. The function is never called.
    46→
    47→Meanwhile, `vtx_deopt_runtime_transition` (the real deopt path called by the JIT deopt stub) does the following at lines 598–613:
    48→```c
    49→vtx_side_table_t *side_table = (deopt_info != NULL) ? deopt_info->side_table : NULL;
    50→vtx_frame_state_t *fs = NULL;
    51→const vtx_side_table_entry_t *st_entry = NULL;
    52→const vtx_reg_map_entry_t *reg_map = NULL;
    53→uint32_t reg_map_count = 0;
    54→
    55→if (side_table) {
    56→    st_entry = vtx_side_table_lookup_entry(side_table, native_pc);
    57→    if (st_entry) {
    58→        fs = vtx_side_table_get_frame_state(side_table, st_entry->frame_state_index);
    59→        reg_map = st_entry->register_map;
    60→        reg_map_count = st_entry->register_map_count;
    61→    }
    62→}
    63→```
    64→Then `fs`, `reg_map`, and `reg_map_count` are **never read again**. The function reads locals from `jit_frame_read(jit_rbp, offset)` (line 672) and the operand stack from spill slots (line 756) — completely ignoring the FrameState chain and register map that the side table was built to provide.
    65→
    66→**Impact:**
    67→- The entire `vtx_osr_down` / `vtx_osr_resolve_node` / `vtx_osr_build_interp_frame` subsystem (~300 lines) is dead code with multiple latent bugs (see OSR-FRAME-6, OSR-FRAME-7, OSR-FRAME-8, OSR-FRAME-9, OSR-FRAME-10, OSR-GC-4, OSR-GC-8, OSR-GC-12, OSR-GC-14).
    68→- The real deopt path (`vtx_deopt_runtime_transition`) does not reconstruct inlined callee frames, does not resolve values via the register map, does not handle T2/T3 deopt (it reads locals from fixed frame slots, which only works for T1), and does not re-acquire monitors.
    69→- Any test that claims to verify OSR-down behavior via `vtx_osr_down` is testing dead code.
    70→
    71→### Killer #2: `VTX_STF_OSR_ENTRY` is never written
    72→
    73→**Verification:** I grepped for every use of `VTX_STF_OSR_ENTRY`:
    74→```
    75→$ grep -rn "VTX_STF_OSR_ENTRY" src/ cpp/
    76→src/deopt/side_table.h:79   ← definition
    77→src/deopt/osr.c:249          ← comment
    78→src/deopt/osr.c:253          ← read (entry->flags & VTX_STF_OSR_ENTRY)
    79→```
    80→Two reads, zero writes. No codegen path ever calls `vtx_side_table_add_entry(..., VTX_STF_OSR_ENTRY)`.
    81→
    82→**Impact:**
    83→- The side-table lookup in `vtx_osr_up` (lines 247–260) iterates all side-table entries looking for one with `VTX_STF_OSR_ENTRY` flag set. It will never find one.
    84→- `vtx_osr_up` falls back to the `bc_pc_map` lookup (lines 265–274). This only works for T1-compiled methods that have a `bc_pc_map` entry at the exact loop header PC.
    85→- For T2/T3 methods (which use the side table for deopt, not `bc_pc_map`), OSR up always fails. The dispatch loop then sets `jit_reenter_pending` (dispatch.c:3117), and the next call re-enters the JIT from method entry — defeating the purpose of OSR.
    86→- The README claims "OSR up/down" is a feature. It is not — it's a fallback to whole-method entry for T2/T3.
    87→
    88→### Killer #3: OSR-up return value is the JIT method's return value
    89→
    90→**File:** `src/interp/dispatch.c:3134-3138`
    91→
    92→```c
    93→bool osr_ok = vtx_osr_up(&osr_frame, method->vtable_index, &cc, osr_pc);
    94→if (!osr_ok) {
    95→    interp->jit_reenter_pending = true;
    96→}
    97→```
    98→
    99→**Bug:** `vtx_osr_up` is declared `bool`. Its body is an inline-asm trampoline that, on success, jumps to JIT code and never returns to C. The JIT code runs to completion, then its epilogue does `ret`, which returns to the C caller of `vtx_osr_up` (i.e., to the instruction after the call in `vtx_interp_run`).
   100→
   101→At that point, RAX contains the JIT method's return value (a NaN-boxed `vtx_value_t`). But the C caller reads AL (the low byte of RAX) as the `bool` return of `vtx_osr_up`.
   102→
   103→For VORTEX's NaN-boxing scheme:
   104→- SMI 0:      `0x7FF8000000000000` → low byte `0x00` → `osr_ok = false`
   105→- SMI 1:      `0x7FF8000000000001` → low byte `0x01` → `osr_ok = true`
   106→- SMI 42:     `0x7FF800000000002A` → low byte `0x2A` → `osr_ok = true`
   107→- undefined:  `0x7FF8000000000000` → low byte `0x00` → `osr_ok = false`
   108→- null:       depends on encoding, often `0x0000000000000000` → low byte `0x00` → `osr_ok = false`
   109→
   110→**Impact:** When the JIT method returns SMI 0, `undefined`, or `null` (common return values), `osr_ok` is false. The dispatch loop sets `jit_reenter_pending = true` (line 3137), and the next call to `vtx_interp_run` for this method re-enters the JIT from method entry (dispatch.c:3029–3036) — re-executing the entire method. Side effects (stores, prints, increments) run twice. For a loop that returns 0, this causes unbounded re-execution.
   111→
   112→**Fix:** `vtx_osr_up` should not return `bool`. It should be declared `void` (since it never returns on success), and the dispatch loop should not check a return value. The `jit_reenter_pending` fallback should be triggered by a different mechanism (e.g., the JIT code calling back into the runtime on failure, or the asm block jumping to a failure label instead of the JIT entry).

   120→#### OSR-1. `vtx_osr_down` is dead code — real deopt ignores FrameState and register map
   121→- **Files:** `src/deopt/osr.c:520-612` (dead), `src/baseline/deopt_stubs.c:598-613` (live)
   122→- **Category:** dead-code / deopt-correctness
   123→- **Code:**
   124→  ```c
   125→  // deopt_stubs.c:605-613 — fs, reg_map, reg_map_count set but never used
   126→  if (side_table) {
   127→      st_entry = vtx_side_table_lookup_entry(side_table, native_pc);
   128→      if (st_entry) {
   129→          fs = vtx_side_table_get_frame_state(side_table, st_entry->frame_state_index);
   130→          reg_map = st_entry->register_map;
   131→          reg_map_count = st_entry->register_map_count;
   132→      }
   133→  }
   134→  // ... then reads locals from jit_frame_read(jit_rbp, offset) at line 672
   135→  ```
   136→- **Impact:** The entire OSR-down path in `osr.c` is never called. The real deopt path does not reconstruct inlined frames, does not use the register map (so T2/T3 register-resident values are lost), does not re-acquire monitors, and falls back to bytecode_pc=0 when the pc_map lookup fails (line 594) — re-executing the method from the beginning.
   137→- **Fix:** Either delete `vtx_osr_down` and fix `vtx_deopt_runtime_transition` to actually use the FrameState/register_map, or wire `vtx_deopt_runtime_transition` to call `vtx_osr_down`.
   138→- **Verified:** Yes — grepped for all call sites of `vtx_osr_down`; zero found.

   140→#### OSR-2. `VTX_STF_OSR_ENTRY` flag is never written by any code generator
   141→- **Files:** `src/deopt/side_table.h:79` (define), `src/dept/osr.c:253` (read), no writes anywhere
   142→- **Category:** osr-entry-registration
   143→- **Impact:** The side-table lookup in `vtx_osr_up` (lines 247–260) never finds an OSR entry. OSR up only succeeds via `bc_pc_map` (T1 only). T2/T3 OSR always fails and falls back to whole-method re-enter.
   144→- **Fix:** In the T2/T3 codegen, when emitting an OSR entry point, call `vtx_side_table_add_entry(table, native_pc_offset, fs_idx, VTX_STF_OSR_ENTRY)`.
   145→- **Verified:** Yes — grepped for `VTX_STF_OSR_ENTRY` across `src/` and `cpp/`.

   147→#### OSR-3. OSR-up return value is the JIT method's return value
   148→- **File:** `src/interp/dispatch.c:3134`
   149→- **Category:** return-value / silent-reexecution
   150→- **Code:**
   151→  ```c
   152→  bool osr_ok = vtx_osr_up(&osr_frame, method->vtable_index, &cc, osr_pc);

   155→- **Impact:** When the JIT method returns SMI 0 / undefined / null (low byte of RAX = 0), `osr_ok` is false and the method is re-executed from PC 0 on the next call. Side effects run twice.
   156→- **Fix:** Declare `vtx_osr_up` as `void` (it never returns on success). Use a different mechanism for the fallback path.
   157→- **Verified:** Yes — confirmed via gcc -O0 -S output (per OSR-ASM-2 agent finding).

   159→#### OSR-4. Stack walker reads return address from `[fp+8]` but JIT frame has it at `[RBP+32]`
   160→- **File:** `src/deopt/stack_walk.c:215-220`
   161→- **Category:** stack-walking / gc-root-scanning
   162→- **Code:**
   163→  ```c
   164→  int vtx_stack_walk_read_return_addr(void *fp, void **out_return_addr) {
   165→      if (!out_return_addr) return -1;
   166→      if (!read_ptr(fp, sizeof(void *), out_return_addr)) return -1;  // reads [fp+8]
   167→      return 0;
   168→  }
   169→  ```
   170→- **Layout** (from `src/baseline/frame_layout.h:73-77`):
   171→  ```
   172→  [RBP+0]  = caller RBP       (VTX_FRAME_CALLER_RBP_OFFSET)
   173→  [RBP+8]  = profile_data     (VTX_FRAME_PROFILE_DATA_OFFSET)
   174→  [RBP+16] = deopt_info       (VTX_FRAME_DEOPT_INFO_OFFSET)
   175→  [RBP+24] = method_ptr       (VTX_FRAME_METHOD_PTR_OFFSET)
   176→  [RBP+32] = return address   (VTX_FRAME_RETURN_ADDR_OFFSET)
   177→  ```
   178→- **Impact:** `vtx_stack_walk_read_return_addr` reads `profile_data` (usually NULL) instead of the return address. The stack walker misclassifies JIT frames as native and stops walking. This breaks GC root scanning, deopt frame chain reconstruction, and profiling for any JIT frame.
   179→- **Fix:** `if (!read_ptr(fp, VTX_FRAME_RETURN_ADDR_OFFSET, out_return_addr)) return -1;`
   180→- **Verified:** Yes — direct read of both files.

   182→#### OSR-5. Side-table OSR entry lookup ignores `loop_header_pc`
   183→- **File:** `src/deopt/osr.c:247-260`
   184→- **Category:** pc-mismatch
   185→- **Code:**
   186→  ```c
   187→  for (uint32_t i = 0; i < vtx_side_table_entry_count(compiled_code->side_table); i++) {
   188→      const vtx_side_table_entry_t *entry = vtx_side_table_get_entry(compiled_code->side_table, i);
   189→      if (entry && (entry->flags & VTX_STF_OSR_ENTRY)) {
   190→          osr_entry = (uint8_t *)compiled_code->entry_point + entry->native_pc_offset;
   191→          break;  // ← picks the FIRST OSR entry, regardless of which loop header
   192→      }
   193→  }
   194→  ```
   195→- **Impact:** If a method has multiple OSR entry points (one per loop header), the side-table lookup picks the first one — entering the JIT at the wrong loop. The `bc_pc_map` lookup (lines 265–274) overwrites this if it finds a match, so the bug only manifests when `bc_pc_map` is NULL or doesn't contain `loop_header_pc`. Combined with OSR-2 (flag never set), this is currently latent.
   196→- **Fix:** Add a `bytecode_pc` field to `vtx_side_table_entry_t` and check it against `loop_header_pc`.
   197→- **Verified:** Yes — direct read.

   199→#### OSR-6. OSR-up asm clobbers callee-saved registers without saving them
   200→- **File:** `src/deopt/osr.c:384-510`
   201→- **Category:** abi-violation
   202→- **Clobber list (line 508):** `"rax", "rbx", "rcx", "rdx", "rsi", "r8", "r9", "r10", "r12", "r13", "r14", "r15", "memory"`
   203→- **Bug:** The asm clobbers RBX, R12, R13, R14, R15 (all callee-saved per System V ABI). The asm jumps to JIT code, which eventually returns via the JIT epilogue. The JIT epilogue (`baseline/codegen.c:1146-1170`) restores RBX and R12 from `[RBP + SAVED_RBX_OFFSET]` and `[RBP + SAVED_R12_OFFSET]` — but the OSR-up asm never initialized these slots. So RBX/R12 are restored from garbage.
   204→- **Impact:** When execution returns to the C caller of `vtx_osr_up` (i.e., `vtx_interp_run`), RBX and R12 contain garbage. `vtx_interp_run` uses these registers for its own state (e.g., the frame pointer, loop variables). Crash or silent wrong behavior shortly after.
   205→- **Fix:** Before jumping to JIT code, save the current RBX/R12/R13/R14/R15 to the JIT frame's saved-register slots (`[RBP + SAVED_RBX_OFFSET]`, etc.). Or, since the JIT epilogue restores from there, initialize those slots from the current register values.
   206→- **Verified:** Yes — direct read of the asm clobber list and the JIT epilogue.

   221→#### OSR-8. `vtx_osr_down` only copies `method_id` and `bytecode_pc` to `interp` — drops locals/stack/monitors/caller chain
   222→- **File:** `src/deopt/osr.c:603-609`
   223→- **Category:** frame-completeness
   224→- **Code:**
   225→  ```c
   226→  if (interp) {
   227→      interp->method_id = new_frame->method_id;

   236→#### OSR-9. `vtx_osr_resolve_node` cannot resolve constants, parameters, or spilled values
   237→- **File:** `src/deopt/osr.c:39-80`
   238→- **Category:** node-resolution
   239→- **Bug:** `vtx_osr_resolve_node` only looks up nodes in the `register_map` (a sparse array of `(node_id, value)` pairs). Constants (`VTX_OP_Constant`), parameters (`VTX_OP_Parameter`), and nodes that were spilled to the stack are NOT in the register map. For these, the function returns `VTX_VALUE_UNDEFINED`.
   240→- **Impact:** Any local or stack slot that holds a constant, a parameter, or a spilled value resolves to `undefined` during OSR-down reconstruction. Silent wrong values.
   241→- **Fix:** Add fallback resolution: for `VTX_OP_Constant`, read the constant value from the node table; for `VTX_OP_Parameter`, read from the JIT frame's local slots; for spilled nodes, read from the spill slots.
   242→- **Verified:** Yes — direct read. (Latent due to OSR-1.)

   244→#### OSR-10. FrameState arena lifetime mismatch — side table holds dangling pointers after compile arena is destroyed
   245→- **File:** `src/deopt/frame_state.c` (arena-allocated), `src/compile/request.c:414` (`vtx_arena_destroy(&compile_arena)`)
   246→- **Category:** lifetime / use-after-free
   247→- **Bug:** `vtx_frame_state_create(arena, ...)` allocates FrameStates from the compilation arena. The side table (`vtx_side_table_t`) stores pointers to these FrameStates in its `frame_states[]` array. When compilation finishes, `request.c:414` destroys the compile arena — freeing all FrameStates. The side table's `frame_states[]` now contains dangling pointers. Any deopt that looks up a FrameState via the side table dereferences freed memory.
   248→- **Impact:** Use-after-free → SIGSEGV on deopt.
   249→- **Fix:** Either deep-copy FrameStates into the side table (malloc'd, not arena), or keep the compile arena alive for the lifetime of the compiled code.
   250→- **Verified:** Yes — direct read of `vtx_frame_state_create` signature and `request.c:414`.

   254→#### OSR-11. OSR-up does not validate compiled_code version/epoch
   255→- **File:** `src/dept/osr.c:201-220`
   256→- **Category:** versioning / use-after-free

   262→#### OSR-12. `vtx_osr_up` does not check for pending safepoints before jumping to JIT code
   263→- **File:** `src/deopt/osr.c` (no safepoint check anywhere in the function)
   264→- **Category:** safepoint / gc / invalidation

   267→- **Fix:** Call `vtx_safepoint_check()` immediately before the asm block.

   270→#### OSR-13. Register map format mismatch between side table and `vtx_osr_resolve_node`
   271→- **File:** `src/deopt/side_table.h:53-56` vs `src/deopt/osr.c:39-80`
   272→- **Category:** register-map-format
   273→- **Side table format:**
   274→  ```c
   275→  typedef struct {
   276→      uint32_t     register_number;
   277→      vtx_nodeid_t node_id;
   278→  } vtx_reg_map_entry_t;  // 8 bytes
   279→  ```
   280→- **OSR resolve format** (from osr.c:43-52):
   281→  ```
   282→  register_map[0] = count (uint32_t in low 32 bits of first vtx_value_t)
   283→  register_map[1..2*N] = (node_id, value) pairs of vtx_value_t
   284→  ```
   285→- **Bug:** The side table stores `vtx_reg_map_entry_t[]` (register_number + node_id). `vtx_osr_resolve_node` expects a flat `vtx_value_t[]` with a count header and (node_id, value) pairs. These are completely different formats. No conversion step exists.
   286→- **Impact:** If `vtx_osr_down` were called (it isn't — see OSR-1), it would interpret the side table's `vtx_reg_map_entry_t[]` as a `vtx_value_t[]`, reading garbage as the count and crashing or returning wrong values.
   287→- **Fix:** Convert the side table's register map to the expected format before passing to `vtx_osr_resolve_node`, or change `vtx_osr_resolve_node` to accept `vtx_reg_map_entry_t[]`.
   288→- **Verified:** Yes — direct read of both definitions.

   478→## 5. Architecture-Level Observations
   479→
   480→Beyond the individual bugs, the OSR subsystem has structural problems:
   481→
   482→1. **Two parallel deopt implementations.** `vtx_osr_down` in `osr.c` is a FrameState-driven implementation that was carefully written (with many "B24 fix" / "B25 fix" / "DEOPT-005 fix" comments) but never wired in. `vtx_deopt_runtime_transition` in `deopt_stubs.c` is the actual implementation, which is much cruder (reads locals from fixed frame slots, ignores the register map, doesn't handle inlining). The existence of two implementations means any fix to one doesn't fix the other.
   483→
   484→2. **OSR entry registration is missing across all tiers.** The `VTX_STF_OSR_ENTRY` flag exists in the side-table schema but no codegen writes it. This suggests the feature was designed (the schema was added) but never implemented (the codegen was never updated to populate it).
   485→
   486→3. **The OSR-up trampoline is x86-64-specific inline asm** that hardcodes frame-layout assumptions, register conventions, and ABI details. This is fragile and makes the "retargetable regalloc" claim (README: "Adding a new architecture only requires implementing a TargetDescription") untrue for OSR — ARM64 and RISC-V cannot OSR without rewriting the trampoline.
   487→
   488→4. **The OSR-up return-value bug (OSR-3)** reveals a fundamental design flaw: `vtx_osr_up` is declared `bool` but never returns on success. The C calling convention has no way to express "this function never returns normally." The correct design is either `void` (with a separate failure path) or `__attribute__((noreturn))` on the success path.
   489→
   490→5. **No integration test for OSR.** The test suite (`tests/`) has no test that verifies: (a) a method executed via OSR produces the same result as via pure interpretation, (b) a deopt after OSR correctly reconstructs the interpreter state, (c) OSR under concurrent GC preserves all roots. Without these tests, the OSR bugs are invisible.
   491→

   494→## 6. Recommended Fix Order
   495→
   496→1. **OSR-1** (dead `vtx_osr_down`): Decide whether to delete it or wire it in. This determines the fix strategy for OSR-7, OSR-8, OSR-9, OSR-13, OSR-14, OSR-15 (all latent in `osr.c`).
   497→2. **OSR-3** (return-value bug): Change `vtx_osr_up` to `void` and remove the `bool osr_ok` check. This is a one-line fix that prevents silent re-execution.
   498→3. **OSR-2** (missing `VTX_STF_OSR_ENTRY`): Add the flag in T2/T3 codegen. Without this, T2/T3 OSR is impossible.
   499→4. **OSR-4** (stack walker offset): One-line fix — use `VTX_FRAME_RETURN_ADDR_OFFSET` instead of `sizeof(void*)`.
   500→5. **OSR-6** (callee-saved clobber): Save RBX/R12/R13/R14/R15 to the JIT frame's saved-register slots before jumping.
   501→6. **OSR-10** (FrameState lifetime): Keep the compile arena alive, or deep-copy FrameStates.
   502→7. **OSR-20/21/22** (concurrent free/NULL): Implement deferred quarantine for code and metadata.
