    10→## 1. Executive Summary
    11→
    12→VORTEX is a multi-tier speculative JIT compiler written in C17 with a C++ embedding API. The codebase implements a computed-goto interpreter (T0), baseline JIT (T1), mid-tier (T1.5), Sea-of-Nodes optimizing JIT (T2), speculative SIMD with deoptless continuations (T3), and background AOT compilation.
    13→
    14→The architecture is ambitious and many subsystems are wired together correctly, but the audit surfaced a substantial number of real defects across every major subsystem. The most dangerous classes are:
    15→
    16→1. **Optimizer miscompilations** — silent wrong-code bugs in `constant_prop`, `algebraic`, `loop_unroll`, `cfg_simplify`, and PEA cross-object scalar replacement. These produce executables that run but return wrong answers, and they bypass testing because the tests rarely exercise the folded/unrolled path.
    17→2. **Register allocator / emitter bugs** — XMM14/XMM15 (reserved spill scratch registers) leak into the allocatable pool; linear-scan interval splitting loses per-vreg state for the first half; SSE mandatory prefixes are emitted in the wrong order so XMM8–XMM15 operands are silently truncated to XMM0–XMM7.
    18→3. **GC correctness** — old-gen pinned objects get copied into young gen during `vtx_gc_collect_young`; Phase-5 swap leaves dangling old→young references; coroutine error path calls `free()` on an mmap'd pointer (UB).
    19→4. **Concurrency** — SIGSEGV fault handler calls `pthread_mutex_lock` (not async-signal-safe → deadlock); spec-version registry returns stale pointers across `realloc`; `vtx_version_enter` has a TOCTOU UAF on the version struct; threadpool workers get stuck in safepoint-nanosleep and never check `shutdown`.
    20→5. **Code cache** — invalidation frees code that another thread may still be executing (the comment explicitly says "DON'T free" but the next line frees it anyway); versioned-cache `on_exit` heuristic frees code that is still running on other threads.
    21→6. **Stack-effect table** — two superinstructions (`LOAD_LOCAL__LOAD_LOCAL` and `LOAD_LOCAL__STORE_FIELD`) have reversed `stack_input_count`/`stack_output_count` in `vtx_opcode_table`, causing OOB operand-stack writes in the interpreter and wrong spill-area sizing in T1.
    22→7. **Public C++ API** — `ShapeTable::add_property` keeps a reference into a `vector` across `emplace_back` (UAF on every shape transition past capacity); `superinstruction::predecode` memcpy overruns the bytecode buffer for truncated final instructions; `host_function` trampoline hard-codes `argc=1` so multi-arg host functions are broken.
    23→

    46→## 3. Top 25 Most Impactful Bugs (Verified or High-Confidence)
    47→
    48→These are the bugs I would fix first — sorted by severity × blast radius. Each has been either directly verified against the source or comes from a high-confidence agent finding with corroborating evidence.

    50→### CRITICAL
    51→
    52→#### C1. Superinstruction stack-effect table is reversed
    53→- **File:** `src/runtime/bytecode.c:131-132`
    54→- **Category:** interpreter-correctness / JIT-correctness
    55→- **Code:**
    56→  ```c
    57→  OP(VTX_OP_LOAD_LOCAL__LOAD_LOCAL,  2, 0, true, 4),  /* push two locals */
    58→  OP(VTX_OP_LOAD_LOCAL__STORE_FIELD, 0, 1, true, 4),  /* push local, store field */
    59→  ```
    60→- **Bug:** Both superinstructions have their `stack_input_count`/`stack_output_count` reversed.
    61→  - `LOAD_LOCAL__LOAD_LOCAL` should be **input=0, output=2** (it pushes two locals, takes nothing).
    62→  - `LOAD_LOCAL__STORE_FIELD` should be **input=2, output=0** (it pops obj+value, stores the field, takes the local from operand).
    63→- **Impact:** Every part of the runtime that consults `vtx_opcode_table[]` for stack-effect (interpreter stack checks, T1 spill-area sizing, verifier) computes the wrong stack depth for these two opcodes. On the interpreter side this allows OOB operand-stack writes; on the JIT side it under-sizes the spill area.
    64→- **Fix:** Swap the two integers on each line.
    65→- **Verified:** Yes — direct read of `bytecode.c`.
    66→
    67→#### C2. `free()` on mmap'd coroutine stack pointer
    68→- **File:** `src/runtime/coroutine.c:106`
    69→- **Category:** memory-safety / UB
    70→- **Code:**
    71→  ```c
    72→  if (getcontext(&co->ctx) != 0) {
    73→      free(co->stack);   // ← co->stack = (char*)mapped + guard_size
    74→      free(co);
    75→      return NULL;
    76→  }
    77→  ```
    78→- **Bug:** `co->stack` is **not** the malloc'd pointer — it is `mapped + guard_size`, pointing into the middle of an mmap'd region (lines 75–94). Calling `free()` on it is undefined behavior (glibc will typically abort with "invalid pointer").
    79→- **Impact:** `vtx_coroutine_create` aborts the process instead of returning NULL on `getcontext` failure.
    80→- **Fix:** `munmap(co->stack_mmap_base, co->stack_mmap_size);` then `free(co);`.
    81→- **Verified:** Yes — direct read of `coroutine.c`.
    82→
    83→#### C3. Old-gen pinned objects get copied into young gen during `vtx_gc_collect_young`
    84→- **File:** `src/runtime/gc.c:1064-1103`
    85→- **Category:** gc-correctness
    86→- **Bug:** Phase 5 of the young collection iterates `gc->pinned_objects[]` and unconditionally copies each pinned object into `young_to`. There is no check for `vtx_gc_in_old(gc, pinned)`. If an old-gen object is pinned (which is legal — `vtx_gc_pin_object` accepts any object), this:
    87→  1. Copies an old-gen object into a young semi-space,
    88→  2. Overwrites the old-gen slot with a forwarding-pointer sentinel — corrupting the old-gen heap metadata (which is not designed to hold forwarding pointers),
    89→  3. Breaks the card-table / mark bitmap for old gen,
    90→  4. May duplicate live objects.
    91→- **Impact:** Heap corruption, use-after-free of old-gen objects, crashes during subsequent collections. Triggered by any code path that pins an old-gen object (e.g. long-lived objects referenced from JIT code that takes a temporary pin).
    92→- **Fix:** Add `if (vtx_gc_in_old(gc, pinned)) continue;` at the top of the Phase-5 loop, or implement separate old-gen pin handling.
    93→- **Verified:** Yes — direct read of `gc.c`. The code even includes a "BUG #6 KNOWN LIMITATION" comment immediately below, but that comment describes a *different* bug (old→young refs), not this one. This one is unaddressed.
    94→
    95→#### C4. Constant-fold of unsigned compares silently returns `false`
    96→- **File:** `src/ir/constant_prop.c:416-424` and `src/ir/algebraic.c:244-252`
    97→- **Category:** optimizer-correctness (miscompilation)
    98→- **Code:** (constant_prop.c)
    99→  ```c
   100→  switch (node->cond) {
   101→  case VTX_COND_EQ:  result = (a == b); break;
   102→  case VTX_COND_NE:  result = (a != b); break;
   103→  case VTX_COND_LT:  result = (a < b);  break;
   104→  case VTX_COND_LE:  result = (a <= b); break;
   105→  case VTX_COND_GT:  result = (a > b);  break;
   106→  case VTX_COND_GE:  result = (a >= b); break;
   107→  default: break;   // ← ULT/ULE/UGT/UGE fall through here
   108→  }
   109→  return vtx_lattice_const_int(result ? 1 : 0);  // result stays false
   110→  ```
   111→- **Bug:** `VTX_OP_Cmp` is the only integer compare opcode; signed-ness is in the `node->cond` field, which can be `VTX_COND_ULT/ULE/UGT/UGE` (defined in `node.h:258-261`). Neither `constant_prop` nor `algebraic` handles these cases — they fall through to `default` and `result` stays `false`.
   112→- **Impact:** Any constant-foldable unsigned compare miscompiles to `false`. Example:
   113→  ```c
   114→  uint32_t x = 5;
   115→  if (x < 10u) { ... }   // ← folds to false; the "then" branch is eliminated
   116→  ```
   117→  This affects array bounds checks, unsigned loop conditions, and hash-code computations. The bug is silent — the code still compiles and runs, it just does the wrong thing.
   118→- **Fix:** Add the four missing cases. For `constant_prop.c`, use `(uint64_t)` casts on `a` and `b` for the unsigned comparisons (currently `a` and `b` are `int64_t`, so a sign-extended unsigned compare would still be wrong).
   119→- **Verified:** Yes — direct read of both files.

   121→#### C5. PEA cross-object scalar replacement uses first-write-wins instead of last-write-wins
   122→- **File:** `src/pea/cross_object_sr.c:497-553`
   123→- **Category:** optimizer-correctness (miscompilation)
   124→- **Code:**
   125→  ```c
   126→  /* First pass: create mappings for all stored field values */
   127→  for (uint32_t n = 0; n < table->count; n++) {
   128→      ...
   129→      if (node->opcode != VTX_OP_StoreField) continue;
   130→      ...
   131→      result->mappings[result->mapping_count].local_id = value_id;
   132→      result->mapping_count++;
   133→  }
   134→  /* Second pass: rewrite LoadField accesses to use the scalar local */
   135→  ...
   136→  for (uint32_t m = 0; m < result->mapping_count; m++) {
   137→      if (result->mappings[m].alloc_id == alloc_id &&
   138→          result->mappings[m].field_offset == node->field_offset) {
   139→          local_id = result->mappings[m].local_id;
   140→          break;   // ← picks the FIRST matching store
   141→      }
   142→  }
   143→  ```
   144→- **Bug:** The first loop records **every** `StoreField` to a given `(alloc_id, field_offset)`. If there are two stores to the same field, both are added to the mapping array. The second loop's lookup uses `break` on the first match, so it picks the **first** store, not the **last**.
   145→- **Impact:** `obj.x = 1; obj.x = 2; return obj.x;` returns `1` instead of `2` after PEA. Wrong code, silent.
   146→- **Fix:** Either (a) overwrite existing mapping entries in the first loop (look up before appending), or (b) iterate the mapping array in reverse in the second loop and `break` on first match.
   147→- **Verified:** Yes — direct read of `cross_object_sr.c`.

   149→#### C6. SIGSEGV handler calls `pthread_mutex_lock` (not async-signal-safe)
   150→- **File:** `src/compile/safepoint.c:434-460` (handler) → `vtx_safepoint_check` at line 453 → mutex locks at lines 96, 108, 315, 357, 495, 531, 607, 772, 793
   151→- **Category:** concurrency (deadlock)
   152→- **Bug:** The guard-page SIGSEGV handler `vtx_guard_page_sigsegv_handler` calls `vtx_safepoint_check(mgr, NULL)`, which takes `manager->install_mutex` and `manager->invalidate_mutex`, and eventually `vtx_deopt_table_mutex`. None of these are async-signal-safe. If the signal interrupts a thread that already holds one of these mutexes, the recursive lock attempt deadlocks the entire process.
   153→- **Impact:** Intermittent process hangs under safepoint-driven deopt. Very hard to reproduce, very easy to hit in production.
   154→- **Fix:** Restructure so the signal handler only flips a flag and returns; defer the actual install/invalidate work to the next normal safepoint poll. Alternatively use `pthread_spin_trylock` and bail out on contention.
   155→- **Verified:** Yes — direct read of `safepoint.c`.
   156→
   157→#### C7. Code cache invalidation frees code while another thread may execute it
   158→- **File:** `src/codecache/invalidate.c:250-308`
   159→- **Category:** memory-safety (UAF on executable code)
   160→- **Bug:** Lines 257, 279, 290 contain comments explicitly saying **"DON'T free the code or metadata here. The code may still be executing on another thread's stack."** Then line 291 immediately calls `vtx_code_cache_free(cache, cm->code_start, cm->code_size)` — which frees the code. Lines 296-308 then NULL out `side_table`, `deopt_info`, `bc_pc_map` (leaking them, since they were allocated separately).
   161→- **Impact:** Use-after-free of native code. A thread that loaded `compiled_code` before invalidation can be executing freed memory. Crashes are intermittent and look like "segfault in random JIT code".
   162→- **Fix:** Move the free to a deferred-quarantine queue that's only drained after a safepoint has confirmed no thread is in JIT code.
   163→- **Verified:** Yes — direct read of `invalidate.c`.

   165→#### C8. XMM14/XMM15 (spill scratch registers) leak into regalloc allocatable pool
   166→- **File:** `src/lower/target.c:138-140`
   167→- **Category:** regalloc-correctness (silent native code corruption)
   168→- **Code:**
   169→  ```c
   170→  if (cls == VTX_REG_CLASS_XMM) {
   171→      return VTX_XMM_ALL_MASK;  /* all 16 XMM regs */
   172→  }
   173→  ```
   174→- **Bug:** `emit.c:2947` defines `VTX_SPILL_XMM_TMP 14` and uses XMM14 (and XMM15 at line 4025) as scratch registers for SSE spill/fill. But the allocatable mask for the XMM class returns all 16 XMM regs, including 14 and 15. Regalloc will happily assign a live vreg to XMM14, then the next spill/fill will clobber it.
   175→- **Impact:** Silent native-code corruption whenever the register allocator is under XMM pressure. Symptoms: floats/doubles in computed values are wrong intermittently; vectorized loops return wrong results.
   176→- **Fix:** `return VTX_XMM_ALL_MASK & ~VTX_XMM_RESERVED_MASK;` where `VTX_XMM_RESERVED_MASK = (1u<<14) | (1u<<15)`.
   177→- **Verified:** Yes — direct read of `target.c` and `emit.c`.
   178→
   179→#### C9. Linear-scan interval splitting loses per-vreg state for the first half
   180→- **File:** `src/lower/regalloc.c:1275-1298` and `1338-1400`
   181→- **Category:** regalloc-correctness
   182→- **Bug:** When the linear scan splits an interval, the second half overwrites `result->vreg_to_phys[vreg]` and `result->vreg_to_spill[vreg]` in the flat per-vreg mappings. The mappings cannot represent both halves. Instructions in the first half's range then read from an uninitialized spill slot (or a register that was never loaded).
   183→- **Impact:** Silent native code corruption under register pressure. Same class of bug as C8 but triggered by spilling rather than by register reuse.
   184→- **Fix:** Per-interval (rather than per-vreg) physical/spill storage, or refuse to split when the vreg already has a spill slot assigned.
   185→- **Verified:** No (not directly read; high-confidence agent finding with specific line numbers).
   186→
   187→#### C10. SSE mandatory prefixes are emitted in the wrong order
   188→- **File:** `src/lower/emit.c` (~15 SSE helper functions)
   189→- **Category:** emit-correctness (silent XMM8-15 truncation)
   190→- **Bug:** Per Intel SDM Vol. 2, the mandatory prefix (66/F2/F3) for SSE instructions must come **before** the REX prefix, and REX must be the **last** prefix before the opcode. The VORTEX emitter emits REX first, then the mandatory prefix, so the REX is ignored and XMM8–XMM15 operands are silently truncated to XMM0–XMM7.
   191→- **Impact:** Any SSE instruction that references XMM8–XMM15 (either as source or destination) silently uses the low 8 XMM register instead. Wrong float/double/SIMD results whenever regalloc assigns a high XMM.
   192→- **Fix:** Reorder prefix emission: legacy prefixes → mandatory prefix → REX → opcode.
   193→- **Verified:** No (high-confidence agent finding).
   194→
   195→#### C11. Loop unroll multi-copy Phi back-edge corruption (factor ≥ 4)
   196→- **File:** `src/ir/loop_unroll.c`
   197→- **Category:** optimizer-correctness (miscompilation)
   198→- **Bug:** The unroller aliases `cur_phi_be_val` to `phi_be_val` instead of allocating a separate array. For factor-2 unrolling this works (one copy of the body, one back-edge). For factor-4+ the second iteration of the unroll body overwrites `phi_be_val` while the first iteration's value is still needed, producing wrong loop-carried values and never wiring the final Phi back-edge.
   199→- **Impact:** Wrong results for any loop unrolled by 4 or more (the default factor is 2, so this is latent unless the factor is bumped).
   200→- **Fix:** Allocate a separate `cur_phi_be_val` array.
   201→- **Verified:** No (high-confidence agent finding).

   203→#### C12. `cfg_simplify` If-elimination creates a self-loop on the taken Proj
   204→- **File:** `src/ir/cfg_simplify.c`
   205→- **Category:** optimizer-correctness
   206→- **Bug:** When eliminating an If whose condition is a known constant, the code calls `vtx_node_replace_all_uses(nt, i, taken_proj)` to rewrite the If's output. But `taken_proj`'s own `inputs[0]` points back to the If. After replacement, `taken_proj.inputs[0]` becomes `taken_proj` itself — a self-loop. Any subsequent pass that walks the control chain hangs or infinite-loops.
   207→- **Impact:** Compiler hang on any constant-foldable branch. Bypassed only because constant branches are usually already eliminated by SCCP before `cfg_simplify` runs.
   208→- **Fix:** Use `vtx_node_replace_input(nt, taken_proj, 0, node->inputs[0])` to explicitly re-wire the Proj's control input to the If's input.
   209→- **Verified:** No (high-confidence agent finding).

   211→#### C13. Spec-version registry returns stale pointer after `realloc`

   215→- **Impact:** UAF on the version registry under concurrent compilation. Intermittent crashes during background AOT.

   219→#### C14. `vtx_version_enter` has a TOCTOU UAF on the version struct

   223→- **Impact:** UAF during tier transition / version swap under concurrent access.

   227→#### C15. `ShapeTable::add_property` keeps a reference into a `vector` across `emplace_back`
   228→- **File:** `cpp/include/vortex/shape.hpp:95-109`
   229→- **Category:** memory-safety (UAF in public C++ API)
   230→- **Bug:** `add_property` takes a reference to an element of `shapes_`, then calls `shapes_.emplace_back(...)` which may reallocate the vector. The reference is now dangling.
   231→- **Impact:** UAF on every shape transition past the vector's current capacity. Public API — affects every embedder.
   232→- **Fix:** Copy out the fields needed before `emplace_back`, or use indices instead of references.

   235→#### C16. `superinstruction::predecode` memcpy overruns the bytecode buffer
   236→- **File:** `cpp/include/vortex/superinstruction.hpp:306`
   237→- **Category:** memory-safety (heap-buffer-overflow in public C++ API)
   238→- **Bug:** `predecode` does `memcpy(dst, bc->code + pc, instr_size)` without checking that `pc + instr_size <= bc->length`. A truncated final instruction reads past the end of `bc->code`.
   239→- **Impact:** Heap-buffer-overflow when loading a malformed or truncated `.vtbc` file. Public API.
   240→- **Fix:** Bounds-check before memcpy; treat truncated instruction as end-of-stream.

   243→#### C17. `superinstruction::try_fuse_pair` OOB read for fusion patterns 2 & 3
   244→- **File:** `cpp/include/vortex/superinstruction.hpp:207, 225, 232`

   259→#### C19. Deopt batcher drops the site_id when full

   275→#### C21. Profile merge drops `total_count` field

   283→#### C22. `test_opcodes_b4_b8.c` has an empty `if (pos >= cap) { /* grow */ }` body
   284→- **File:** `tests/opcode/test_opcodes_b4_b8.c:48`
   285→- **Category:** memory-safety (OOB write in test)
   286→- **Code:**
   287→  ```c
   288→  static void b_op(builder_t *b, uint8_t op) {
   289→      if (b->pos >= b->cap) { /* grow */ }
   290→      b->buf[b->pos++] = op;
   291→  }
   292→  ```
   293→- **Bug:** The grow branch is empty. The function unconditionally writes past the buffer.
   294→- **Impact:** Tests that overflow the arena-allocated builder buffer corrupt the arena. Latent because tests usually pick generous caps.
   295→- **Fix:** Either grow the buffer (arena-alloc a bigger one and memcpy), or `assert(b->pos < b->cap)`.
   296→- **Verified:** Yes — direct read.

   345→## 4. False Positives Detected During Verification
   346→
   347→The audit agents are aggressive by design — they cast a wide net. During spot-check verification I found **at least one significant false positive** that I explicitly removed from the report above:
   348→
   349→### FP1: "Systematic opcode-value mismatch in scripts/gen_vortex_bench_bytecode.py"
   350→
   351→One agent reported that `scripts/gen_vortex_bench_bytecode.py`, `tests/opcode/test_opcodes.c`, and `benchmarks/measure_si_gain.c` all hardcode control-flow opcode values that are "+6 too high" relative to the real `VTX_OP_*` enum. The agent claimed `OP_GOTO=41` should be `35`, etc.
   352→
   353→I verified this directly by reading `src/runtime/bytecode.h:25-158` (the enum definition) and counting:
   354→`HALT=0, NOP=1, LOAD_LOCAL=2, ..., FCMP_GE=40, GOTO=41, IF_TRUE=42, IF_FALSE=43, CALL_STATIC=44, CALL_VIRTUAL=45, CALL_INTERFACE=46, RETURN=47, RETURN_VALUE=48, ...`
   355→
   356→The Python script's values (`GOTO=41, IF_TRUE=42, IF_FALSE=43, RETURN_VALUE=48`) are **correct**. The agent was confused — they appear to have looked at the *algebraic.c* `Cmp(x,x) → Constant(1)` switch (which uses different opcode names like `VTX_COND_*`) and conflated the two namespaces.
   357→
   358→**Lesson for the reader:** When fixing any individual bug below, re-verify against the source first. The agents are reliable for *most* findings but produce occasional false positives, especially when reasoning about cross-file invariants.

   373→## 6. Recommendations
   374→
   375→1. **Add a CI gate that runs the test suite under TSan + UBSan.** The single highest-leverage action. Many of the concurrency and UB bugs (C2, C6, C7, C13, C14, H7, H14) would surface immediately.
   376→2. **Add an IR verifier pass** (`VORTEX_ENABLE_VERIFY`) and run it after every optimization pass in CI. The optimizer miscompilations (C4, C5, C11, C12) are silently wrong; a verifier that checks use-list consistency, dominator-tree validity, and Phi input counts would catch the structural bugs.
   377→3. **Add a differential test** that runs every program through T0, T1, and T2 and asserts identical results. This catches optimizer miscompilations that the current unit tests miss.
   378→4. **Add a fuzz target for the bytecode loader.** Several public-API OOB reads (C16, C17, H25) are reachable from a malformed `.vtbc` file.
   379→5. **Fix the superinstruction stack-effect table first** (C1). It's a two-character fix and unblocks correct stack-effect reasoning everywhere else.
   380→6. **Fix the unsigned-compare constant fold** (C4) second. It's a four-case-per-file fix and prevents silent miscompilation of every constant-foldable unsigned compare.
   381→7. **Quarantine freed code** in the code cache (C7, H14) before any other cache work.
   382→8. **Restructure the SIGSEGV handler** (C6) to defer all mutex-taking work out of the signal path.

   405→## 8. Methodology and Caveats
   406→
   407→- **8 sub-agents** ran in parallel, each scoped to one slice of the codebase to avoid context-window pressure and to keep depth per file high.
   408→- The CMake build was not runnable in the audit environment (no `cmake` binary available, no `sudo`). Compile-time issues were therefore found via `gcc -fsyntax-only -Wall -Wextra` on individual files where the agent chose to do so. This means some warnings/errors that only appear during a full link may be missed.
   409→- Static analyzers (`cppcheck`, `clang-tidy`) were not available; all findings are by manual code reading.
   410→- The audit is **static only** — no runtime tests were run. Bugs that only manifest at runtime (especially concurrency bugs) are inferred from code structure, not demonstrated.
   411→- I directly verified 7 of the most critical findings (C1, C2, C3, C4, C5, C6, C7, C8, C22) by reading the source. The remaining critical/high findings come from the agents and are high-confidence but not independently verified.
   412→- At least one significant false positive (FP1 above) was caught during verification. Treat the agent-reported bugs as candidates, not as confirmed, before fixing.
   413→- The `rust-bindings/vendor/` directory is a verbatim copy of `src/` and was **not** separately audited. Bugs found in `src/` apply equally to the vendored copy.
